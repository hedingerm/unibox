# Unibox — Kontext & Design-Entscheidungen

Desktop-Unibox für alle E-Mail-Konten eines Entwicklers: Gmail/Google-Workspace-Konten und Resend-Domains in einer gemergten Inbox, vollwertiger Client (lesen, verwalten, senden). Persönliches Tool zuerst, aber produktfähig gedacht.

Stand: 2026-08-20 (Grilling-Session abgeschlossen, vom Owner bestätigt).

## Stack

- **Electron + React + TypeScript**, SQLite (better-sqlite3 im Main-Prozess)
- Credentials von Tag 1 im OS-Keychain, keine Hardcodes
- Runtime-Präferenz: Bun wo möglich (Electron-Main ist Node-gebunden)

## Konten & Anbindung

### Google (Gmail API, kein IMAP)
- 2 Konten: 1× privat `@gmail.com`, 1× Workspace (Custom Domain)
- Gmail REST API wegen Labels, Threads, `history.list`-Inkrementell-Sync
- Send-as-Aliase via `sendAs`-API lesen; beim Antworten automatisch die Alias-Adresse wählen, an die die Mail ging (im Compose übersteuerbar)
- **Die `sendAs`-Liste wird bei jedem Sync neu gelesen**, nicht nur beim Erst-Import: Gmail führt für Einstellungen keine History-Einträge, ein dort geänderter Alias oder eine geänderte Signatur käme sonst nie an.
- **Gmail gibt pro Alias genau eine Signatur heraus.** Die Mehrfach-Signaturen aus den Gmail-Einstellungen kennt die API nicht — sie sind hier nicht holbar, sondern nur von Hand nachzutragen. Darum gewinnt eine hier bearbeitete Signatur gegen den Sync: `gmail_signature_html` merkt sich den zuletzt übernommenen Text, und nur solange er mit dem angezeigten übereinstimmt, folgt die Signatur weiter Gmail (löscht Gmail sie, wird sie auch hier leer). Der Standard-Absender ist genauso lokale Präferenz und wird nur beim ersten Import von Gmail gesetzt.
- **Unbestätigte Aliase werden importiert, aber nicht angeboten.** Sie tragen eine Signatur; sie wegzuwerfen hiesse, sie und die lokalen Änderungen an der Zeile bis zur Bestätigung zu verlieren. Sie stehen mit `verified = 0` in der DB, fehlen im Absender-Picker und in `ownAddresses()`, und der nächste Sync schaltet sie frei.
- Zwei-Wege-Sync: archivieren, Labels setzen/entfernen, gelesen/ungelesen, löschen → synct zurück zu Gmail (Offline-Mutations-Queue)
- Antworten werden über das Konto gesendet, das die Mail erhalten hat (Gmail API `send`, Thread bleibt intakt)
- OAuth: externer Client im **Testing-Modus** (Refresh-Tokens laufen nach 7 Tagen ab → wöchentliches Re-Connect akzeptiert; testet den Reconnect-Flow gratis mit). Verifizierung (CASA, restricted scope `gmail.modify`) erst im Produktisierungs-Meilenstein.

### Resend (REST API, kein IMAP — gibt es dort nicht)
- App nimmt einen API-Key entgegen, listet alle Domains, User wählt pro Domain, ob Empfang aktiviert wird
- Empfang aktivieren = Resend-seitig per API einschalten + benötigten MX-Record anzeigen (`inbound-smtp.<region>.amazonaws.com`, Root der Domain, Catch-all `*@domain`) + Verifizierung pollen
- **MX-Konflikt-Warnung ist Pflicht**: hat die Domain bereits einen fremden MX (z. B. Google Workspace), würde Aktivierung die bestehende Mail kapern → App warnt explizit
- Sync per **Polling** der REST-Endpoints (received + sent Emails), kein Webhook / keine Server-Infrastruktur (ein Webhook bräuchte eine öffentliche HTTPS-URL — die hat eine Desktop-App nicht). Resend pollt auf eigenem, schnellerem Takt (15 s) als der volle Gmail-Sync, weil es keinerlei Push-Kanal gibt. Gmail fragt zusätzlich alle 15 s pro Konto nur die `historyId` ab (`users.getProfile`, 1 Quota-Einheit) und startet den History-Sync nur, wenn sie sich bewegt hat.
- Der **erste Sync eines Kontos ist stumm**: er importiert bis zu 30 Tage Historie, das sind keine neuen Mails. Notifications erst ab dem zweiten Zyklus.
- **30-Tage-Retention** bei Resend (gesendet UND empfangen): lokale DB ist die einzige Langzeitquelle → Backup der DB ist Pflicht, nicht Nice-to-have
- Senden über feste, vom User hinterlegte Absenderidentitäten pro Domain (Anzeigename + Adresse), plus „benutzerdefiniert" als Escape-Hatch

## Unibox-Semantik

- **Gemergte Inbox als Default** über alle Google-Konten + Resend-Domains, Konto-Badge pro Zeile
- Sidebar: eigene Sektion je Google-Konto (mit dessen Gmail-Labels) und **je Resend-Domain** (jede Domain verhält sich wie ein eigenes Konto; dass alle am selben API-Key hängen, bleibt unsichtbar)
- Labels bleiben konto-gebunden — kein globales Label-Mergen (`Kunden` in Konto A ≠ `Kunden` in Konto B)
- Threading: Gmail nativ; Resend lokal via `Message-ID`/`In-Reply-To`/`References`
- Desktop-Notifications ab dem ersten Entwurf, pro Konto/Domain an-/abschaltbar

## Daten

- **Volle Historie** lokal in SQLite (kompletter Erst-Sync aller Konten)
- Volltextsuche: SQLite **FTS5** über alle Konten in einem Index, filterbar nach Konto/Label
- **Such-Operatoren** (Gmail-Syntax, englische Namen — das ist die eingeübte Muskelerinnerung): `from: to: cc: subject: label: in: is:unread|read|starred has:attachment filename: account: after: before: newer_than: older_than:`, `-` negiert, `"…"` ist eine Phrase, `from:me`/`to:me` löst Konto- und Identitäts-Adressen auf. Datumsangaben ISO **und** `31.1.2026`. Unbekannte Präfixe (`Re:`, URLs) bleiben Freitext. Kein `OR`, keine Mehrfachwerte — bewusst weggelassen.
  - Eine Operator-Query sucht im ganzen Konto, nicht im geöffneten Label (sonst antwortet `is:unread` im Label `Kunden` mit einem verwirrenden Nichts). Papierkorb/Spam bleiben draussen, ausser die Query sagt `in:trash`/`in:spam`.
  - Ergebnisse werden in SQL nach Thread gruppiert, das LIMIT zählt Konversationen. Treffer-Nachricht = die neueste passende im Thread.
  - Bekannte Semantik: Filter greifen pro Nachricht, angezeigt wird der Thread — `-is:unread` kann also einen Thread zeigen, der als ungelesen erscheint (eine andere Nachricht darin ist ungelesen).
  - Adressen liegen normalisiert in `message_addresses` (kind/email/name, indexiert): `from:`/`to:`/`cc:` treffen damit exakt statt als Substring im JSON-Blob, und die Suchbox hat eine Absenderliste zum Vervollständigen. Migration 3 füllt die Tabelle per `json_each` nach.
  - Die Suchbox vervollständigt Operatoren, Absender (aus `message_addresses`, neueste zuerst), Labels, Konten und Werte von `is:`/`in:`/`has:` — ↑/↓, Enter/Tab, Esc.
  - Gespeicherte Suchen liegen in den App-Settings (`savedSearches`) und stehen als eigene Sidebar-Sektion; ein Klick füllt die Suchbox, ändert also keine Mailbox-Auswahl.
- Attachments: Gmail on demand laden + cachen; **Resend sofort komplett sichern** (30-Tage-Fenster erzwingt das)

## Schreibassistent im Compose

- **Eine Mechanik: `@ai <Anweisung>` + Enter** direkt im Mailtext. Die Zeile ist ein Befehl, kein Mailtext — sie verlässt den Entwurf, bevor der Job startet. Shift+Enter bleibt ein Zeilenumbruch, `@ai` ohne Anweisung bleibt Text. Der Stern-Button tippt nur `@ai ` für dich; „Text korrigieren" startet direkt eine reine Sprachkorrektur.
- **Drei Modi, ein Primitiv:** `draft` (leerer Body → Claude schreibt), `rewrite` (gefüllter Body → Claude überarbeitet nach Anweisung), `correct` (nur Rechtschreibung, Grammatik, Zeichensetzung — kein Umstellen, kein Kürzen).
- **Der Job lebt im Main-Prozess, nicht im Fenster.** Compose schliessen bricht nichts ab; das Ergebnis kommt als Toast mit „Öffnen", der das Compose-Fenster mit demselben Kontext wieder aufbaut. Jobs liegen nur im Speicher — ein App-Neustart verwirft laufende Jobs, bewusst: ein Entwurf ist kein Datenbestand.
- **Review nur, wo es etwas zu vergleichen gibt.** Bei leerem Entwurf landet der Text direkt in der Mail — ein Diff gegen nichts sagt nichts. Überarbeitung und Korrektur gehen durch das Review: der Wort-Diff (`lib/diff.ts`) zeigt jede Änderung als eigene Entscheidung, per Klick einzeln an- oder abwählbar. Änderungen, die nur ein Leerzeichen trennt, werden zu einer Entscheidung zusammengefasst — sonst liesse sich aus „Hallo"→„Guten Tag" ein „Hallo Tag" zusammenklicken, das niemand vorgeschlagen hat. Über einen Absatzumbruch hinweg wird nicht zusammengefasst.
- **Signatur und zitiertes Original sind eigene Editor-Blöcke.** tiptap kennt kein `<div>`: ohne eigenen Node verliert beides beim ersten Durchlauf seinen Marker und wird zu gewöhnlichen Absätzen. Dann zählt die Signatur als „der Nutzer hat schon etwas geschrieben" (Diff statt Direkteinsatz), das Zitat gilt als eigener Entwurf, und ein Identitätswechsel stapelt Signaturen statt sie zu ersetzen. Ein leerer Entwurf bekommt darum immer einen Absatz **vor** der Signatur, sonst sitzt der Cursor beim Öffnen in der Signatur.
- **Claude bekommt Text, nicht HTML** — die Absätze baut der Renderer. Das hält Markdown-Zäune und Inline-Styles aus dem Editor, und das Modell kann kein Markup einschleusen.
- **Der Stil steht in den Einstellungen** (`aiStylePrompt`), vorbelegt mit einer neutralen Vorlage, die jeder Nutzer auf die eigene Stimme umschreibt. Die CLI läuft gesandboxt (keine Tools, keine MCP, keine Settings-Quellen) und lädt darum auch keine Skills — was nicht im Prompt steht, weiss das Modell nicht.
- **Der Empfänger ist Kontext, auch ohne Verlauf.** Eine neue Mail hat keinen Thread, aus dem sich Anrede, Sprache und Ton ablesen liessen — bei einer vagen Anweisung („frag ihn wegen der Offerte") müsste das Modell alle drei erfinden. Darum baut `ai/recipients.ts` aus dem Archiv ein Dossier pro Empfänger: Name, Du/Sie, die zuletzt benutzte Anrede und Schlussformel im Wortlaut, letzter Kontakt, Anzahl Mails, dazu bis zu vier kurze Auszüge früherer Post. Gesucht wird kontoübergreifend — wer jemanden kennt, kennt ihn nicht pro Postfach.
- **Du oder Sie wird abgelesen, nicht geraten.** Gelesen wird zuerst in den *eigenen* ausgehenden Mails an die Adresse — wie man jemanden anspricht, ist die Sache, die reproduziert werden soll. Es entscheidet die **neueste** Mail mit einem Befund, nicht die Mehrheit: aus Sie wird du, und eine lange Sie-Geschichte darf die Mail, in der das passiert ist, nicht überstimmen. Formale Treffer werden gross geschrieben gesucht (`Ihnen`, `Ihr…`), und ein `Sie` zählt nur mitten im Satz — am Satzanfang sind es dieselben drei Buchstaben wie die dritte Person Plural. Ohne Befund bleibt die Zeile weg: eine fehlende Angabe kostet eine Vermutung, eine falsche die Mail.
- **Die Sprache wird nicht erkannt.** Ein Stopwort-Zähler hat am ersten echten Beispiel („Hoi Max, chasch du mir die Offerte no schicke?") nichts gefunden — Schweizerdeutsch ist der Normalfall, nicht die Ausnahme. Die wörtliche Anrede und die Auszüge zeigen die Sprache ohnehin, und eine falsch benannte Sprache in einer Regel, der das Modell folgen soll, ist schlimmer als gar keine.
- **Gezählt wird nur, was der Absender selbst geschrieben hat.** `ownWords()` schneidet den zitierten Vorgänger weg — ohne das misst ein „Sie" aus dem Zitat die andere Person, und ein Du-Verhältnis kippt beim ersten weitergeleiteten Behördenbrief.
- **Der Verlauf schlägt das Dossier.** Bei einer Antwort reisen nur die Kopfzeilen mit, keine Auszüge: die konkrete Konversation steht schon im Prompt, ältere Post würde sie nur nach hinten drücken. Abgeleitet wird trotzdem aus allem, was zur Adresse im Archiv liegt.
- **Eine Korrektur bekommt kein Dossier.** Sie darf nur Sprache richten; Kontext ist genau der Weg, auf dem eine Korrektur anfängt, den Inhalt zu verbessern.
- **Verteiler haben keinen Empfänger.** Bleiben nach dem Filtern mehr als drei Adressen übrig, entsteht *gar kein* Dossier — nicht drei davon: ein Rundschreiben hat keine Beziehung, die sich beschreiben liesse, und drei willkürlich herausgegriffene Dossiers würden eine behaupten. Eigene Adressen und Maschinenmailboxen fallen vorher weg, über `isNoReplyAddress` — dieselbe Liste, die auch entscheidet, ob eine Mail auf Antwort wartet.
- **Die eigene Post wird eigens geholt, nicht aus den neuesten herausgefiltert.** Wer öfter schreibt als angeschrieben wird — Wochenrapporte, Statusmails —, drückt sonst jede eigene Mail aus dem Fenster; die Rückfallregel ist für „nie geschrieben" gedacht, nicht für „vor einem Monat geschrieben". Zwei eigene Mails sind darum auch in den Auszügen gesetzt, wo es sie gibt: wie der Empfänger schreibt, zählt weniger als wie man ihm schreibt.
- **Unter der Grussformel wird nicht mehr gezählt.** Gesendete Mail kommt mit Signatur zurück, und eine Fusszeile wie „Besuchen Sie uns auf …" ist ein Sie in *jeder* eigenen Mail. Eine kurze Du-Mail („Hoi Marco. Passt so. Gruass") hat kein eigenes Pronomen, das dagegenhält — sie kippte zuverlässig auf Sie.
- **Die Anrede zählt als Befund.** Genau diese kurzen Mails haben sonst überhaupt kein Signal. „Hoi Marco" ist ein Du, „Sehr geehrte" ein Sie — und ein Nachname schlägt den freundlichen Ton: „Hallo Herr Meier" ist ein Sie.
- **Verlauf und Entwurf sind Eingabedaten**, nicht Anweisungen: derselbe Injection-Riegel wie beim Settle-Prompt. Der zitierte Teil eines Weiterleitens bleibt ganz draussen — fremde Mail wird weder gelesen noch umgeschrieben.

## Antworten

- **Die Antwort entsteht im Gespräch.** Ein Klick auf die Antwortzeile klappt denselben Editor an ihrer Stelle auf (`reply-inline`), der Verlauf darüber rückt hoch, der Cursor steht schon im Text. Das Fenster ist der Sonderfall, nicht der Normalfall: es kommt über „In eigenem Fenster öffnen", über Weiterleiten und über eine neue Mail.
- **Ein Composer, zwei Rahmen.** `ComposeSeed.mode` entscheidet nur, wer die Komponente rendert — Lesebereich oder App-Shell. Autosave, Assistent, Anhänge und Senden sind in beiden Formen dieselbe Mechanik, damit keine zweite halbe Compose-Implementierung entsteht.
- **Der Wechsel ins Fenster übergibt den Entwurf**, nicht nur den Text: die Leiste sichert erst und schaltet dann ihr Autosave ab, sonst legt das Fenster mit seinem ersten Speichern einen zweiten Entwurf an.
- **Der Cursor kommt von tiptap, nicht aus einem Effekt.** `autofocus: 'start'` setzt ihn beim Bauen des Editors; ein `editor.commands.focus()` im Effekt greift unter StrictMode auf die bereits zerstörte Instanz zu — das war ein weisser Bildschirm. Der Inline-Test rendert darum in `<StrictMode>`.
- **Die Leiste gehört zur Konversation.** Wer sie verlässt, schliesst sie — geschrieben wird beim Verlassen weggesichert. Ein unsichtbares Compose würde sonst die Tastaturkürzel blockieren.
- **`ComposeSeed.seq` ist der React-Key des Composers.** Das Fenster hält seine eigene Kopie des Entwurfs — in `useState` und im Editor —, die beim Setzen eines neuen Seeds nicht neu gelesen wird. Ohne neuen Key zeigte ein zweites `openCompose` weiter die alte Mail; mit ihm wird ausgehängt, und genau das Aushängen schreibt den bisherigen Entwurf weg.

## Links

- **Ein Link in der Mail geht in den Browser.** Der Sanitizer setzt `target="_blank"`, der `setWindowOpenHandler` des Fensters fängt das Popup ab und reicht die Adresse an `shell.openExternal` weiter — im Fenster selbst wird nie navigiert, das würde den offenen Entwurf verwerfen.
- **`mailto:` bleibt in der App.** An das Betriebssystem gereicht öffnete es irgendeinen anderen Mailclient, und die Antwort läge in einem Postfach, das diese Inbox nie sieht. Der Main-Prozess erkennt das Schema, holt das Fenster nach vorne und schickt `compose:mailto` an den Renderer; `parseMailto` liest `to/cc/bcc/subject/body`. Das `+` ist dabei in der Adresse ein echtes Plus und im Query-Wert ein Leerzeichen — dasselbe Zeichen mit zwei Bedeutungen in einer URL.
- **Das Schema wird im Main entschieden, nicht im Fenster.** `shell:openUrl` lässt nur `http`, `https` und `mailto` durch: Mail-HTML erreicht diesen Aufruf, und ein `file:` wäre etwas auf diesem Rechner. Der Sanitizer ist nur eine Umschreibung von einem Fehler entfernt.
- **Die Adresse steht da, bevor sie gefolgt wird.** In der Mail ist der Linktext regelmässig etwas anderes als das Ziel — absichtlich. Beim Überfahren zeigt eine Statuszeile unten links, wohin es geht; das Kontextmenü auf dem Link kann öffnen und die Adresse kopieren.
- **Im Entwurf öffnet erst Cmd+Klick.** `openOnClick` würde jedem Klick folgen, und dann liesse sich der Cursor nicht mehr in einen Link setzen — ein Entwurf ist zum Bearbeiten da.

## Kontextmenü im Composer

- **Das Menü handelt an der Stelle, an der es geöffnet wurde.** Ein Rechtsklick bewegt den Cursor von sich aus nicht, also setzt der Handler ihn — ausser der Klick liegt in einer bestehenden Auswahl, denn eine Auswahl anzuklicken *ist* die Geste, und sie zu verwerfen nähme ihr den Sinn. `posAtCoords` kann werfen, wo es kein Layout gibt; ein Fehlschlag ist ein `null`, kein abgestürzter Handler.
- **Die Auswahl wird vom Editor gemalt, nicht vom Browser.** Ein `contenteditable` ohne Fokus bekommt vom Browser gar keine Auswahl gezeichnet — der Rechtsklick nimmt den Fokus ins Menü, und damit verschwand genau der Text, um den es im Menü geht. Eine Inline-Decoration übernimmt das, solange der Editor den Fokus nicht hat. Fokus steht nicht im Editor-State, ein Blur allein rechnet also nichts neu: die leere Transaktion in `blur`/`focus` ist das, was die Decoration nochmals anschauen lässt. Sie ändert das Dokument nicht, das Autosave liest sie darum nicht als Bearbeitung.
- **Einfügen läuft über den Main-Prozess.** `navigator.clipboard.readText` braucht einen Secure Context und eine Berechtigung, die die gepackte App beide nicht hat. Eingefügt wird reiner Text: formatiertes Einfügen schmuggelte fremde Styles in den Entwurf, und Formatierung kommt aus der Leiste.
- **Der Assistent bekommt hier eine Stelle statt der ganzen Mail** (Modus `spot`). Markiert = ersetzen, blosser Cursor = Lücke füllen. Das Eingabefeld sitzt *im* Menü, nicht in einem Dialog: das Menü ist das, was die Stelle mitbringt — ein Dialog ginge mit der Auswahl schon hinter sich auf.
- **Die Umgebung reist mit, die Stelle ist markiert.** `AiSpot.draft` ist der ganze Entwurf als Text mit `\u0001`/`\u0002` um die Stelle, im Prompt zu `<stelle>…</stelle>` übersetzt. Ein Spot-Edit ohne Umgebung liefert einen Satz, der für sich richtig ist und dort, wo er steht, falsch. Signatur und Zitat bleiben draussen: fremde Worte und die eigene Fusszeile sind nichts, wonach sich ein Satz richten soll.
- **Gebaut wird die Stelle im Fenster, nicht im Main.** Dort ist die Auswahl exakt; ein Fragment im Main durch Suchen wiederzufinden griffe beim ersten wiederholten Wort daneben.
- **Zurückgeschrieben wird zuerst an den gemerkten Bereich**, solange dort noch dieselben Worte stehen. Danach wird der Text im Entwurf gesucht — der Job überlebt das Fenster, und Positionen überleben es nicht. Findet sich nichts, wird nichts eingesetzt und es steht da: eine geratene Stelle schriebe die Antwort dorthin, wohin niemand gezeigt hat. Eine blosse Lücke hat keine Worte zum Wiederfinden.
- **Review nur bei zwei Seiten.** Eine ersetzte Markierung geht durch den Wort-Diff, eine gefüllte Lücke direkt in den Entwurf — dieselbe Regel wie bei `draft` gegen `rewrite`.

## Zurückstellen (Snooze)

- **Snooze ist Archivieren mit Wecker.** Die Gmail-API kennt kein Snooze — das ist eine reine Weboberflächen-Funktion —, also wird aus den zwei Zügen gebaut, die es gibt: jetzt archivieren, später wieder in den Eingang legen. Beide Hälften laufen durch dieselbe Mutations-Queue wie ein Archivieren von Hand, mit demselben Offline-Verhalten.
- **Zwei Folgen, bewusst in Kauf genommen.** Eine zurückgestellte Mail liegt bei Gmail im Archiv, nicht in Gmails eigenem „Später"-Ordner — wer dort nachschaut, sieht sie nicht. Und geweckt wird nur, solange Unibox läuft: das Versprechen lautet „nicht vor", nicht „genau um". Beim Start wird darum sofort geprüft, sonst käme ein über Nacht fälliger Wecker nie an. Beides steht im Menü, wo die Entscheidung fällt.
- **Der Wecker gehört zum Thread**, nicht zur Nachricht — das ist die Einheit, auf die der Nutzer klickt. Eine Zeile pro Konversation in `snoozes` (Migration 8), erneutes Zurückstellen verschiebt die Zeit, statt einen zweiten Wecker zu stapeln.
- **Neue Post im Thread beendet den Snooze sofort.** Ein Zurückstellen ist die Erinnerung, sich noch zu kümmern; eine Antwort *ist* diese Erinnerung, nur früher. Gemessen wird an der höchsten Nachrichten-`rowid`, die der Thread beim Zurückstellen hatte — nicht an einem Zeitstempel: so hängt nichts daran, welche Uhr die Mail gestempelt hat, und zwei in derselben Millisekunde gespeicherte Mails bleiben unterscheidbar. Eigene Antworten wecken nicht.
- **Papierkorb, Spam, endgültig löschen und Entarchivieren löschen den Wecker.** Die Mail hat den Eingang endgültig verlassen (oder ist schon zurück) — sie später nochmals hervorzuholen würde genau die Entscheidung rückgängig machen, die eben gefallen ist.
- **Die Liste ist kein Label.** Zurückgestellte Mail ist archivierte Mail plus lokale Zeile, kein Label hält sie zusammen — darum bekommt `MailboxSelection` ein `view`, und die Sidebar-Zeile steht kontoübergreifend unter „Alle Eingänge". Sie zählt, was wartet, nicht was ungelesen ist, und verschwindet, sobald nichts mehr wartet — ausser man steht gerade darin.
- **Die Rückkehr steht auf der Zeile.** Das Datum der Zeile sagt, wann zuletzt etwas passiert ist; das einzige, was an einer zurückgestellten Mail noch vor einem liegt, ist die Rückkehr — die steht als eigenes Badge daneben. Sortiert wird trotzdem nach Nachrichtendatum: wer den Eingang leer hält, findet eine zurückkommende Mail auch ohne Sprung nach oben.
- **Jede Zeile im Menü nennt ihr Datum.** „Nächste Woche" ohne Datum ist ein Versprechen, das niemand nachprüfen kann. Angebote, die nach hinten zeigen würden, fehlen ganz statt in die Vergangenheit zu deuten — „Heute Abend" ab 16 Uhr, „Am Wochenende" ab Freitag. `b` nimmt das eine Angebot, das keine Entscheidung ist (morgen früh); in der Snooze-Liste bedeutet dieselbe Taste das Gegenteil und holt zurück.

## Wartet auf Antwort (Follow-ups)

- **Das Gegenstück zum Eingang.** `settle` sortiert ein, was hereinkommt; das hier merkt sich, was hinausging und noch keine Antwort hat. Beides ist lokal, beides ist aus der Mail rekonstruierbar — es gibt bei Gmail und Resend kein Feld dafür und es braucht auch keines.
- **Standardmässig an, mit einem Klick weg.** Der Fall, für den das existiert, ist die Mail, die man nachfassen wollte und vergessen hat — ein Angebot, das man erst annehmen muss, wäre dieselbe Falle einen Schritt weiter. Die Leiste im Compose ist darum angehakt, sobald mindestens eine echte Person angeschrieben ist. Maschinenadressen (`no-reply@`, `bounce-…@`) und Verteiler über fünf Empfänger bekommen die Zusage gar nicht erst angeboten: sie antworten nie, und eine Erinnerung darauf wäre nur Lärm.
- **Werktage, nicht Kalendertage.** Freitag + 3 ist Mittwoch. Alles andere hiesse, dass eine Freitagsmail montags als überfällig gilt, obwohl niemand Zeit hatte zu antworten.
- **Die Erinnerung löst sich selbst auf.** Nach jedem Sync prüft `reconcile()` nur die Konversationen, die tatsächlich warten: schreibt jemand zurück, ist die Sache erledigt und verschwindet lautlos. Abhaken muss man nichts — das war der ganze Punkt.
- **Eine Abwesenheitsnotiz ist keine Antwort.** Gmails eigener Urlaubsantworter behält den Betreff und markiert sich nur im Header, darum trägt jede Nachricht ein `auto_reply` aus `Auto-Submitted`, `Precedence` und `List-Id` (Migration 9). Zusätzlich greifen Betreff („Automatische Antwort:", „Abwesenheitsnotiz", „Out of office") und Absender — wobei „AW:" ausdrücklich *nicht* zählt, das ist schweizerdeutsches „Re:" und damit die echteste Antwort, die es gibt.
- **„Seit wann" misst an der Speicherzeit, nicht am `Date`-Header.** Ein Absender mit falscher Uhr datiert seine Antwort sonst vor die Mail, die sie beantwortet, und die Erinnerung stünde ewig. Die Position im Thread ist der erste Massstab, die Speicherzeit der zweite — und sie wandert mit dem Anker mit, sonst zählte dasselbe Nachfassen bei jedem Durchlauf erneut.
- **Nachfassen verlängert, statt zu beenden.** Schreibt man selbst nochmals in einen wartenden Thread, rückt der Anker auf diese Mail und die Frist beginnt von vorn; die Zeile zählt mit, wie oft das passiert ist. Eine Konversation hat immer genau eine offene Erinnerung — ein partieller Unique-Index macht die zweite unmöglich.
- **Das Häkchen im Compose bewaffnet nur, es entwaffnet nie.** Wer es bei einer Antwort wegklickt, meint diese Mail, nicht die Erinnerung, die eine frühere gesetzt hat. Beendet wird eine Erinnerung dort, wo man sieht, was man beendet: in der Konversation, über „Erledigt".
- **Papierkorb, Spam und endgültig löschen beenden das Warten.** Dem Papierkorb ist keine Antwort geschuldet.
- **Auch diese Liste ist kein Label** — sie nutzt dasselbe `view` wie der Snooze und steht kontoübergreifend unter „Alle Eingänge", sortiert nach Fälligkeit statt nach Datum. Der Countdown hängt aber an *jeder* Zeile, nicht nur in dieser Mailbox: dass man ihn im Eingang sieht, ist es, was die Mail überhaupt nicht in Vergessenheit geraten lässt. Überfällig ist der einzige Zustand mit eigener Farbe — ein laufender Countdown ist Information, ein abgelaufener eine Aufgabe.
- **Gemeldet wird genau einmal.** `notified_at` hält die Erinnerung davon ab, sich bei jedem Sync-Zyklus zu wiederholen — das wäre der schnellste Weg, Benachrichtigungen ganz abzuschalten. Verschiebt man die Frist, meldet sie sich neu.
- **Ein Versand, dessen Folge-Sync scheiterte, geht nicht verloren.** Die Zeile entsteht trotzdem, ohne Konversation, bleibt aus allen Listen draussen und wird vom nächsten `reconcile()` adoptiert, sobald die Nachricht auf der Platte liegt. Nach sieben Tagen ohne Nachricht wird sie verworfen.

## Entwürfe

- **Autosave statt Nachfragen.** Das Compose-Fenster schreibt sich nach 1,5 s Tipppause, bei jeder Feldänderung und beim Schliessen in die lokale DB (Tabelle `drafts`, Migration 4). Schliessen ist kein Verwerfen mehr; der Titelbalken sagt, wann zuletzt gesichert wurde. Verworfen wird nur über den Papierkorb-Knopf, und der fragt nach.
- **Ein Entwurf ist Bearbeitungsstand, keine Mail.** Empfänger liegen so in der DB, wie sie getippt wurden — auch halb fertig —, der Body samt Signatur wie im Editor. Erst beim Senden wird daraus eine `OutboxDraft` mit geparsten Adressen.
- **Nichts entsteht ungefragt.** Eine Antwort öffnet mit Empfänger und Betreff; wird nichts getippt, bleibt kein Entwurf zurück (Vergleich gegen den Öffnungsstand).
- **Jedes Konto hat einen Entwürfe-Ordner**, Resend-Domains eingeschlossen: serverseitige Entwürfe gibt es dort nicht, lokale schon. Bei Google stehen die eigenen und die von Gmail geholten Entwürfe in derselben Liste, weil beide dieselbe lokale Zeile sind (siehe Gmail-Spiegelung).
- **Klick auf eine Entwurfszeile öffnet das Fenster**, in dem sie geschrieben wurde (⏎ bei Tastaturnavigation); ein Entwurf hat keinen Lesebereich, weil es nichts zu lesen gibt.
- **Autosave scheitert leise nach aussen, nicht nach innen**: ein Fehler steht dort, wo sonst der Speicherzeitpunkt steht, und wirft nie in den Tippfluss.

### Gmail-Spiegelung

- **Jeder Autosave eines Google-Kontos geht über die Mutations-Queue zu Gmail** (`draft_upsert`/`draft_delete`), also mit demselben Offline-Verhalten und Backoff wie Archivieren. Ein noch wartender Push desselben Entwurfs wird ersetzt statt gestapelt — Gmail ersetzt den Entwurf ohnehin ganz. Queue-Läufe sind serialisiert, sonst legten zwei gleichzeitige Drains denselben Entwurf zweimal an.
- **Gmail führt Entwurfs-ID und Nachrichten-ID getrennt**: eine Bearbeitung behält die Entwurfs-ID und tauscht die Nachricht darin aus. Beide werden lokal geführt, darum erkennt der Sync eine fremde Änderung, ohne jedes Mal den Body zu holen.
- **Der Pull läuft nach dem Nachrichten-Sync**, und die Queue wird davor geleert: sonst meldete der Abgleich Konflikte gegen die eigene, noch nicht gesendete Arbeit.
- **Konflikt = zweite Kopie, nie stilles Überschreiben.** Haben beide Seiten geändert, landet die Gmail-Version als eigener Entwurf mit Suffix „(Konflikt)" und behält die Verknüpfung; die lokalen Änderungen bleiben stehen und werden als neuer Gmail-Entwurf angelegt. Verschwindet ein Entwurf bei Gmail, wird die lokale Kopie gelöscht — ausser es hängen ungesicherte lokale Änderungen dran, dann wird sie selbstständig.
- **Der Entwürfe-Ordner zeigt nur noch lokale Entwürfe**: Gmails DRAFT-Nachrichten werden in dieselben lokalen Entwürfe gezogen, ein zweiter, nicht editierbarer Eintrag pro Zeile wäre nur Verwirrung.
- **Anhänge fremder Entwürfe werden mitgeholt**, sonst verlöre eine Bearbeitung hier die Dateien. Bekannte Grenze: Inline-Bilder aus dem Editor reisen als `data:`-URIs in den Gmail-Entwurf (erst beim Senden werden daraus CID-Teile).

## Vorlagen

- **Eine Vorlage ist eine dritte Signatur.** Wiederverwendbarer Mailtext gehört keinem Konto — dieselbe Offerte geht unter einem Gmail-Alias so raus wie unter einer Resend-Adresse —, also liegt sie in einer eigenen Tabelle neben `signatures` (Migration 13) und nicht in den App-Settings: gespeicherte Suchen sind kurze Strings, ein Vorlagentext ist ein HTML-Blob mit Bildern.
- **Platzhalter sind Text, kein Knoten.** `{{empfaenger.vorname}}` steht als gewöhnlicher Text im Body: tiptap speichert ihn unverändert, der Assistent liest ihn als Text, und das Schema muss keinen weiteren markierten Block lernen. Ein `<span>` mit Marker hätte denselben Weg genommen wie Signatur und Zitat — und dieselben Sonderfälle mitgebracht.
- **Zwei Klassen, nach einer Frage getrennt: weiss der Entwurf die Antwort schon?** Empfänger, Absender, Betreff und Datum füllt der Composer selbst; alles andere — `{{Betrag}}`, `{{Projekt}}` — fragt *ein* Dialog vor dem Einfügen ab. Abgebrochen heisst: es wird nichts eingefügt, nicht „halb eingefügt".
- **Der Name des Empfängers kommt aus dem Archiv**, nicht aus dem Feld: `search:addresses` liefert ihn zu einer blossen Adresse, dieselbe Quelle, aus der auch das Empfänger-Dossier des Assistenten liest. Wer schon einmal angeschrieben wurde, kennt seinen Namen.
- **Nicht Gewusstes wird gefragt, nicht geraten.** `{{empfaenger.vorname}}` ohne bekannten Namen bleibt offen und landet im Dialog. Ein leer gelassenes Feld füllt nichts — der Platzhalter bleibt sichtbar stehen, und genau den findet die Sendesperre.
- **Ein offener Platzhalter verlässt das Haus nicht.** `{{betrag}}` in einer gesendeten Mail ist schlimmer als eine nicht gesendete. Geprüft wird nur, was der Nutzer geschrieben hat — ein zitiertes Original mit geschweiften Klammern ist fremder Text.
- **Zwei Wege hinein, einer hindurch.** `/kürzel` plus Enter im Body benutzt denselben `onEnterCommand`-Haken wie `@ai` (die Trigger können nicht kollidieren: Schrägstrich gegen Klammeraffe), der Picker neben der Signaturwahl ist der Mausweg. Beide laufen durch dieselbe Funktion, und die setzt den Text über Signatur und Zitat — die dreiteilige Ordnung des Entwurfs gilt auch hier.
- **Der Betreff wird nur genommen, wenn keiner dasteht.** Ein „Re: …" wurde absichtlich geschrieben; eine Vorlage überschreibt es nicht.
- **Das Kürzel ist eindeutig, ohne Rücksicht auf Gross- und Kleinschreibung** (partieller Unique-Index, NULL beliebig oft) — sonst hätte `/offerte` zwei Antworten. Die Kollision meldet sich mit dem Kürzel im Klartext, nicht mit SQLite-Wortlaut.
- **Die Platzhalterliste wird abgeleitet, nicht gespeichert.** Was eine Vorlage enthält, sagt ihr Text; eine zweite Kopie davon liefe beim ersten Edit auseinander.

## Verwaltung (ab v0.3)

Die Einstellungen sind kein Modal mehr, sondern ein eigener Arbeitsbereich im MailFlare-Admin-Stil (`g v`, Befehlspalette, Zahnrad in der Kopfleiste). Er ersetzt die Mailbox-Ansicht, bis „Zurück zur Mail“ geklickt wird. Cloudflare-Begriffe aus MailFlare sind auf Resend abgebildet; es gibt weiterhin keinen Server.

| Seite | MailFlare/Cloudflare | Hier |
| --- | --- | --- |
| Übersicht | Dashboard | Zustand von Konten, Domains, Regeln und Zustellung, jüngste Aktivität |
| Domains | DNS-Provisioning, Email Routing | Resend-Domains mit Status-Chips, Empfang-Schalter (Catch-all), DNS-Panel (SPF, DKIM, Return-Path aus Resend; Empfangs-MX und DMARC live per DNS), „DNS prüfen“ = Resend `verify`. „Neue Domain“ legt sie per `POST /domains` an (Name + Region, die Region ist danach fix) und klappt gleich die Einträge auf. |
| Postfächer | Mailboxen | lokale **Ansichten** auf den Catch-all, keine Resend-Objekte (siehe unten) |
| Routing | Routing-Regeln | lokale Regeln, beim Abruf angewendet |
| Zustellung | Webhooks / send_email-Logs | Zustellstatus gesendeter Mail (gepollt) + Verwaltung der Resend-Webhooks für *fremde* Endpunkte |
| Konten, Identitäten, Vorlagen, Mitteilungen, Warteschlange, Aktivität, Backups, Allgemein | — | die früheren Einstellungs-Tabs, dazu Aktivitätslog und Backup-Liste |

- **Postfächer sind Adressfilter, keine Labels.** Ein Postfach (Adresse + Aliase auf einer Resend-Domain, optional eine Standard-Identität) zeigt die Konversationen, deren Nachricht im gewählten Label an eine dieser Adressen ging (To/Cc) — standardmässig im Eingang. Gelöscht wird nur die Ansicht, nie Mail. „Nicht zugeordnet“ ist der Rest: eingehende Mail einer Domain an keine ihrer Postfach-Adressen. `mailbox:counts` liefert dafür `unassigned:<accountId>` pro Domain (plus `unassigned` als Summe für die Verwaltung), die Zeile steht unter jeder Domain mit Postfächern. Reihenfolge per Pfeilen oder Drag & Drop.
- **Routing-Regeln** (Feld × Bedingung × Wert → Aktion) gelten nur für Resend-Mail, pro Domain oder für alle. Sie laufen beim Import neu empfangener Mail, **nicht rückwirkend** und ohne Review-Schritt — sie sind explizite Konfiguration; jede Aktion landet im Aktivitätslog. Reihenfolge = Priorität, von oben nach unten; die erste passende Regel beendet den Durchlauf, ausser „Weitere Regeln stoppen“ ist aus. Aktionen: Label, Archivieren, gelesen, Spam, Papierkorb, Weiterleiten, Verwerfen. Regex ist case-insensitiv, auf 500 Zeichen begrenzt, der Body auf 20 000 Zeichen gekürzt; ein ungültiger Ausdruck wird beim Speichern abgelehnt. Weitergeleitete Mail trägt eine Marke und wird nie ein zweites Mal weitergeleitet; Weiterleiten an eine eigene Catch-all-Domain ist verboten (Schleife). „Testen“ probiert die Regel vor dem Speichern an den zuletzt empfangenen Mails.
- **Zustellung wird gepollt, nicht gepusht.** Die Sent-Liste von Resend trägt `last_event` pro Mail, also kostet der Status keinen Zusatz-Request. Grenzen: aktualisiert wird im normalen Abruf-Takt (15 s), nur solange Resend die Mail listet (30 Tage), und ein Zyklus blättert nur so weit, bis eine ganze Seite bekannt ist — Statuswechsel sehr alter Mails (jenseits der ersten Seite, 100 Mails) kommen darum nicht mehr an. Zwischenereignisse zwischen zwei Abrufen (z. B. `delivered` → `opened`) sieht man nur als letzten Stand. Webhooks bräuchten eine öffentliche URL; die Seite verwaltet sie nur für andere Systeme, das Signing-Secret wird einmal gezeigt.
- **Aktivitätslog** (`activity`-Tabelle): gesendete Mail, Regelaktionen, angelegte Domains, Empfang an/aus, Konten, Backups, Sync-Fehler (gleichartige werden gefaltet).

## Design (ab v0.3)

- **Die Optik folgt MailFlare, nicht mehr den macOS-Mockups**. Getönter App-Grund (`#f6f8fc`), randlose weisse Flächen darauf, grosse Radien, Nav-Einträge als Pillen mit `--accent-soft` für den aktiven, Sektionstitel 11px in Versalien, Unread-Zähler als Pill-Badge.
- **Alle Farben laufen über Tokens** in `styles.css` (`:root`). Komponenten schreiben keine Hex-Werte mehr (Ausnahme: Konto- und Labelfarben, die sind Daten). Icons nehmen `var(--…)` als Strichfarbe.
- **Eine Formensprache für alles Schwebende:** Dialoge, Prompts, Sheets (Aufräumen, Onboarding), Viewer (Anhang, Original) und Palette teilen `--radius-dialog` (20px), einen linksbündigen Titel ohne graue Titelleiste und dieselben Felder (12px-Radius) wie die Verwaltung. Menüs und Vorschlagslisten sind Popover mit `--radius-lg` und Haarlinie (die braucht der Dark Mode), der aktive Eintrag in `--accent-soft`. Buttons sind Pillen (`button-primary`/`button-secondary`), Status sind getönte Chips mit Icon. Banner (offline, neu verbinden, Fehler) sind eingerückte runde Streifen im weissen Panel, keine randvollen Balken.
- **Dark Mode ist drin.** Einstellung *Darstellung* (Wie das System / Hell / Dunkel, `settings.theme`, fehlt = System). Der Renderer setzt `<html data-theme>` und folgt bei „System“ live `prefers-color-scheme`; der Main-Prozess setzt `nativeTheme.themeSource` gleich, damit native Menüs und Scrollbars mitziehen. Die letzte Wahl liegt zusätzlich im localStorage, damit ein dunkles Fenster beim Start nicht weiss aufblitzt.
- **Mail-Inhalte bleiben auf weissem Papier**, auch im Dunkeln (wie Gmail): fremdes HTML ist für eine weisse Seite geschrieben, Umfärben bricht mehr, als es hilft. Gilt auch für Signatur-Vorschau und Signatur/Zitat im Composer.
- **Geist Sans/Mono sind mitgebündelt** (`@fontsource-variable/*`), keine Web-Fonts zur Laufzeit — die App muss offline gleich aussehen.
- **Layout:** Sidebar (Logo, „Schreiben“-Pill, Konten-Sektionen) ist in der Breite ziehbar (200–360px) und auf eine Icon-Leiste einklappbar (☰ oben links); die Liste ist gegen den Lesebereich ziehbar (280–900px). Breiten und Einklapp-Zustand sind reine Fensterpräferenz und liegen im localStorage, nicht in den Settings.
- **Aktionen:** die Suche ist eine breite Pill in der Kopfleiste (`/` springt hinein). ⌘K öffnet die Befehlspalette, `?` die Übersicht der Tastenkürzel; alle Kürzel stehen in einer Liste (`lib/shortcuts.ts`), `g …`-Sequenzen warten eine Sekunde auf die zweite Taste. Die Einstellung „Tastenkürzel aktiv“ schaltet die Einzeltasten ab, ⌘-Kombinationen und Esc bleiben. Die Aktionen auf die Auswahl stehen über dem Lesebereich, die Liste hat „Alle auswählen“, Anzahl und Aktualisieren. Die Hover-Buttons einer Zeile (Archivieren, Löschen, gelesen/ungelesen, Zurückstellen) wirken **nur auf diese Zeile**, unabhängig von der Auswahl — genau dafür sind sie da.
- **Der Stern ist das Systemlabel `STARRED`**, auf beiden Seiten: Gmail synct es zwei-wegig über die Mutations-Queue wie gelesen/ungelesen, eine Resend-Domain hält es als lokales Label. Darum findet `is:starred` beides ohne Sonderfall. Ein Thread gilt als markiert, sobald eine Nachricht es ist (`ThreadSummary.starred`); Markieren setzt den Stern auf die neueste Nachricht (wie Gmail), Entfernen nimmt ihn von allen — sonst hielte eine ältere den Thread markiert. „Markiert“ steht immer unter „Alle Eingänge“ (`view: 'starred'`), kontoübergreifend. Kein Rückgängig-Toast: der zweite Klick auf den Stern *ist* das Rückgängig, und die Zeile kippt sofort, ohne auf den Roundtrip zu warten.
- **Der Composer schwebt unten rechts** (MailFlare): dunkle Titelleiste mit Betreff, minimieren (nur die Leiste bleibt am unteren Rand), vergrössern (zentriert, abgedunkelt — nur dann `aria-modal`), schliessen. Minimiert wird versteckt, nicht ausgehängt: Editor-Undo und Autosave-Timer leben weiter. Tab bleibt im Fenster wie bisher. Cc/Bcc sind Umschalter in der An-Zeile; Blindkopien reisen jetzt mit Entwurf und Versand. Unten: Senden als Split-Button (der Pfeil öffnet „Später senden“), Formatierung, Anhang, Assistent, Korrektur, ⋮, Papierkorb. Signatur, Vorlage und Antwort-Erinnerung stehen auf einer Haarlinien-Zeile darüber. Die Inline-Antwort ist dieselbe Mechanik als abgerundete Karte.
- **Zitierter Verlauf klappt hinter „•••“ weg.** Getrennt wird *vor* dem Sanitizer, weil der die Ids und Attribute entfernt, an denen Outlook (`#divRplyFwdMsg`) und Apple Mail (`blockquote[type=cite]`) ihr Zitat markieren; Gmail markiert per Klasse. Alles ab der Marke in Dokumentreihenfolge gehört zum Zitat (Outlook stellt die alte Mail neben, nicht in den Kopfblock). Eine Mail, die nur aus Zitat besteht, und Weiterleitungen bleiben ganz — dort ist das „Zitat“ der Inhalt. Textmails: der abschliessende `>`-Block samt „Am … schrieb …:“-Zeile.
- **„Original anzeigen“ holt die Rohfassung auf Abruf** (`messages:source`): Gmail `format=raw`, Resend über die `raw.download_url` des empfangenen Mails, sofern die API sie liefert. Gespeichert wird sie nie. Geht das nicht (offline, gesendete Resend-Mail), wird aus den gespeicherten Kopfzeilen und Bodies rekonstruiert — und der Dialog sagt das.
